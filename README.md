# Point Wallet Service (DDD + Redis + Kafka)

## 📌 프로젝트 배경
현재 회사에서 **선불 서비스**를 운영 중이며, 신규로 **적립 포인트** 기능이 필요하여 요구사항을 구현해보고자 합니다.

포인트 시스템은 **대용량 트래픽**, **포인트 사용 시 동시성 문제**, **정산/원장 이력 관리**, **만료 처리** 등 높은 수준의 안정성과 확장성을 요구합니다.

따라서, 이번 프로젝트는 이러한 요구사항을 대비하여 **도메인 주도 설계(DDD)** 를 기반으로 포인트 기능을 구현하고,  
대용량 환경에서도 안정적으로 동작할 수 있도록 **Redis(분산 락 + 캐싱)**, **Kafka(이벤트 기반 비동기 처리)** 를 적용한 **실전형 아키텍처 구축**을 목표로 합니다.

# 🔗 전체 아키텍처

```
[Controller]
     ↓
[Application Service]
     ↓ (Redis Distributed Lock)
[Domain Layer – PointWallet Aggregate]
     ↓
[RDB(H2) 저장]
     ↓
[Kafka Producer] → point-events
     ↓
-----------------------------------------------------
   LedgerConsumer → 원장 DB 저장
   ExpireConsumer → 만료 처리 자동화
   NotificationConsumer → 문자/푸시 알림
-----------------------------------------------------
[Redis Cache] → balance, snapshot 저장
```

# 🧩 주요 구현 범위

## ✔ Point Wallet
- 회원 단위 포인트 지갑 Aggregate
- 포인트 적립/사용/적립취소/사용취소 처리
- 만료일, 잔여 금액, 적립 유형, 상태를 기준으로 사용 가능 포인트 계산

## ✔ 동시성 및 멱등성
- Redis 분산 락을 통한 회원 단위 포인트 변경 동시성 제어
- 주문번호 기준 포인트 사용 멱등성 처리
- Redis 캐시를 통한 지갑/정책 조회 성능 보완

## ✔ 캐시 전략
### Point Wallet 캐시
- 조회 경로는 cache-aside 패턴을 사용하며, 캐시 miss 시 Redis 기반 재생성 락으로 동일 키의 동시 DB 조회를 완화
- 지갑 조회는 한 인스턴스만 DB에서 캐시를 재구성하고, 다른 인스턴스는 짧게 재조회하여 cache stampede를 방지
- 쓰기 경로(적립/사용/취소)는 캐시 값을 정합성 판단 기준으로 사용하지 않고, DB 기준으로 처리한 뒤 캐시를 무효화
- 즉, 캐시는 조회 성능을 위한 보조 수단으로 활용하고, 포인트 차감 가능 여부 같은 핵심 검증은 원본 데이터 기준으로 수행

### Point Policy 캐시
- 포인트 정책과 메타데이터는 읽기 비중이 높고 변경 빈도가 낮은 데이터로 가정
- 동일 시점 대량 만료를 피하기 위해 TTL jitter를 적용해 캐시 만료 시점을 분산
- TTL이 지난 직후에도 짧게 이전 값을 활용하는 stale-while-revalidate 전략을 통해 응답 안정성과 DB 보호를 함께 고려
- 자주 조회되는 정책/핫키는 필요 시 선갱신(pre-warm) 전략으로 캐시 재생성 비용을 분산

## ✔ 운영 고려사항
### 회원 단위 쓰기 락 경합
- 포인트 적립/사용/취소와 같은 쓰기 요청은 회원 식별자 기준 Redis 분산 락으로 직렬화한다
- 이 구조는 동일 회원에 대한 동시 수정 충돌을 줄이는 데 효과적이지만, 트래픽이 매우 몰리는 상황에서는 일부 요청이 오래 대기하거나 락 획득 타임아웃으로 실패할 수 있다
- 즉, 현재 구조는 dead lock 을 적극적으로 만드는 형태라기보다 "순서를 기다리다가 처리 실패가 발생할 수 있는 구조"에 더 가깝다
- 운영 환경에서는 재시도 정책, 짧은 백오프, 사용자 친화적 오류 메시지, 특정 회원에 요청이 집중되는지에 대한 모니터링을 함께 고려할 수 있다

### 캐시 재구성 fallback
- 지갑 조회와 정책 조회 모두 캐시 miss 시 한 인스턴스가 먼저 캐시를 복구하고, 다른 인스턴스는 바로 DB로 내려가지 않고 짧게 재조회하도록 설계했다
- 이 방식은 일반적인 cache stampede 를 완화하는 데 효과적이지만, 락을 획득한 인스턴스의 처리 지연이 길어지거나 Redis 상태가 불안정하면 재조회 구간이 끝난 뒤 일부 요청이 fallback 으로 DB를 직접 조회할 수 있다
- 따라서 현재 구조는 "평상시에는 DB 보호 효과가 크고, 극단적인 지연 상황에서는 제한적으로 DB fallback 을 허용하는 구조"라고 볼 수 있다
- 이후 운영 환경에서는 stale 값 반환 범위 확대, fallback 제한, 재조회 간격 조정, 핫키 선갱신(pre-warm) 같은 방식으로 DB 보호 수준을 더 끌어올릴 수 있다

### 다중 회원 연산 확장 시 락 순서
- 현재 구현은 대부분의 쓰기 요청이 한 번에 하나의 회원 락만 획득하므로, 여러 락이 서로를 기다리는 순환 대기 구조가 생길 가능성이 낮다
- 다만 향후 회원 간 포인트 이동, 선물, 통합 정산처럼 한 요청이 두 명 이상의 회원 상태를 동시에 변경해야 하는 기능이 추가되면 이야기가 달라진다
- 이런 다중 회원 연산에서는 락 획득 순서가 뒤섞일 경우 dead lock 위험이 현실적으로 커질 수 있으므로, memberId 오름차순 락 획득 같은 일관된 규칙을 미리 두는 편이 안전하다
- 또한 다중 락 시나리오에서는 타임아웃, 부분 실패 시 롤백 기준, 재시도 정책까지 함께 설계해야 운영 중 예측 가능한 동작을 만들 수 있다

## ✔ Kafka 이벤트 기반 확장
- 포인트 변경 이벤트를 `point-events` 토픽으로 발행
- `LedgerConsumer`가 이벤트를 소비해 원장 테이블(`point_ledger`)에 이력 저장
- `eventId`와 DB 유니크 제약을 이용해 원장 중복 저장 방지

## ✔ Point Ledger
- `PointWallet`은 현재 포인트 상태를 책임지고, `PointLedger`는 변경 이력을 책임지도록 분리
- 적립/사용/적립취소/사용취소 이벤트를 정산·감사 가능한 append-only 이력으로 보존
- 향후 정산, CS 추적, 통계성 조회로 확장 가능

# 🧭 향후 확장 방향

- Kafka 발행 신뢰성 보강: Outbox 패턴을 도입해 DB 변경과 이벤트 발행 사이의 유실 가능성 완화
- 만료 처리 자동화: 만료 이벤트 타입 추가, 만료 대상 조회/처리 서비스 구현, 만료 결과 원장 기록
- 알림/배치 연동: 포인트 변경 이벤트를 기반으로 알림 서비스와 배치 시스템 확장
- 운영 DB 전환: H2 기반 개발 환경에서 PostgreSQL/MySQL 등 실서비스 DB로 확장
